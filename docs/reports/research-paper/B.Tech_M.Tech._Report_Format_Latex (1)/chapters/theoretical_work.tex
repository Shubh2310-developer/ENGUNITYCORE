\section{Design Philosophy}
\label{sec:design-philosophy}

Engunity was designed around three principles: \textbf{traceability} (every module has defined inputs, outputs, and failure modes), \textbf{replaceability} (components communicate through typed interfaces), and \textbf{observability} (every pipeline stage emits structured streaming events). These principles translate into strict plane separation, Server-Sent Events (SSE) for streaming, Pydantic schemas for all API contracts, and Celery for background job isolation.

\section{The OmniRAG Pipeline}
\label{sec:omnirag}

\subsection{Design Rationale}
\label{subsec:omnirag-rationale}

Early in development, Engunity had separate endpoints for simple questions, document search, and deep research. Empirical observation showed that students routinely underestimated query complexity and ended up on the wrong endpoint. The fix was automatic classification and internal routing: the pipeline exposes a single \texttt{process\_query} method; the strategy is an implementation detail hidden from the user.

\subsection{Complexity Classification}
\label{subsec:complexity-classifier}

The \texttt{QueryComplexityClassifier} is a fine-tuned DistilBERT model (66M parameters) trained on 18,500 manually labelled queries across four complexity tiers from Natural Questions (simple), HotpotQA (multi-hop), and custom engineering-domain queries.

\begin{table}[ht]
    \centering
    \caption{OmniRAG complexity classes, strategies, and query characteristics.}
    \label{tab:complexity}
    \renewcommand{\arraystretch}{1.3}
    \begin{tabular}{llp{5cm}}
        \toprule
        \textbf{Class} & \textbf{Strategy} & \textbf{Characteristics} \\
        \midrule
        \texttt{SIMPLE} & Direct generation & Conversational, definitional, no document dependency \\
        \texttt{SINGLE\_HOP} & Vector RAG + HyDE & Factual with clear document anchor, single retrieval topic \\
        \texttt{MULTI\_HOP} & Graph RAG map-reduce & Comparative, requires synthesis across multiple sources \\
        \texttt{RECURSIVE\_INTENSIVE} & Recursive chain-of-thought & Open-ended analytical, benefits from multi-step reasoning \\
        \bottomrule
    \end{tabular}
\end{table}

The classifier achieves 91.3\% macro-averaged F1 on a held-out test set of 2,000 queries. Misclassification is most common at the SINGLE\_HOP/MULTI\_HOP boundary, which is architecturally benign: routing a SINGLE\_HOP query to the MULTI\_HOP path costs slightly more compute but does not degrade answer quality.

\subsection{Single-Hop Retrieval Flow}
\label{subsec:single-hop}

For standard single-hop queries the pipeline executes a seven-stage sequence: (1) fetch user session summary and process any attached images via CLIP and YOLOv8n; (2) rewrite the raw query and generate 3 variants plus a HyDE hypothetical document; (3) concurrent FAISS semantic search (top-20, cosine) and BM25 keyword search, merged as $s = 0.6 \cdot s_{dense} + 0.4 \cdot s_{sparse}$; (4) FlashRank neural re-ranking to select top-10 chunks; (5) CRAG confidence evaluation---if max score $< 0.6$, trigger Brave Search API web fallback; (6) extractive contextual compression, reducing context tokens by 60--70\%; (7) streaming response generation with SelfCritique evaluation and optional regeneration if score $< 1.8/3.0$.

\subsection{Multi-Hop and Recursive Flows}
\label{subsec:multihop}

The multi-hop path retrieves knowledge-graph community summaries alongside standard vector chunks and synthesises them via map-reduce: the map phase generates partial answers concurrently per community summary and document chunk; the reduce phase synthesises a coherent final response, identifying agreements and resolving contradictions. Recursive queries expand the retrieval budget ($k=40$ versus $k=20$) and hand the assembled context to \texttt{RecursiveReasoningAgent}, which implements a chain-of-thought loop where each step can spawn subsidiary inferences.

\section{The DeepResearchAgent}
\label{sec:deepresearch}

The DeepResearchAgent is an autonomous agent conducting iterative, multi-phase research over vector, web, and graph sources, implemented as an async state machine: \texttt{DECOMPOSE} $\rightarrow$ \texttt{SEARCH} $\rightarrow$ \texttt{EVALUATE} $\rightarrow$ \texttt{REFINE} $\rightarrow$ \texttt{SYNTHESIZE}.

\begin{table}[ht]
    \centering
    \caption{ResearchDepth parameter matrix controlling agent behaviour.}
    \label{tab:depth}
    \renewcommand{\arraystretch}{1.3}
    \begin{tabular}{lrrrl}
        \toprule
        \textbf{Depth} & \textbf{Max Sub-Q} & \textbf{Max Iter} & \textbf{Min Src} & \textbf{Typical Use} \\
        \midrule
        \texttt{QUICK}      & 2  & 1 & 2  & Quick factual look-up \\
        \texttt{STANDARD}   & 5  & 3 & 4  & Coursework research \\
        \texttt{DEEP}       & 8  & 5 & 7  & Thesis-level questions \\
        \texttt{EXHAUSTIVE} & 12 & 8 & 10 & Full domain survey \\
        \bottomrule
    \end{tabular}
\end{table}

\textbf{Phase 1 -- Decompose:} The \texttt{PlannerAgent} generates typed sub-questions (factual, comparative, causal, definitional) bounded by \texttt{max\_sub\_questions}.

\textbf{Phase 2 -- Search:} For each sub-question, the \texttt{SearchAgent} executes three concurrent retrieval operations: FAISS vector search, Brave Search API web search, and knowledge graph community traversal. Results are deduplicated by URL/chunk ID.

\textbf{Phase 3 -- Evaluate:} The \texttt{EvaluatorAgent} scores each evidence item on relevance (0.4 threshold) and identifies gap sub-questions where the evidence pool contains fewer than \texttt{min\_sources} items.

\textbf{Phase 4 -- Refine:} For each gap sub-question, an additional search iteration executes, potentially broadening query terms or switching sources. This loop runs until all sub-questions are evidenced or \texttt{max\_iterations} is reached.

\textbf{Phase 5 -- Synthesize:} The \texttt{SynthesizerAgent} generates a structured research report in one of three formats (detailed, summary, bullet points), with each claim linked to its source evidence via citation markers.

\section{Multimodal Visual Perception}
\label{sec:multimodal}

The \texttt{MultiModalVisionProcessor} wraps three perception components:

\begin{itemize}
    \item \textbf{CLIP (ViT-B/32)}: Embeds each image into the same 512-dimensional space as text, enabling cross-modal retrieval within the same FAISS index. Processing time: $\approx$45\,ms on CPU.
    \item \textbf{EasyOCR}: Extracts printed and handwritten text with bounding box coordinates, preserving spatial relationships for matrix equations and multi-line derivations.
    \item \textbf{YOLOv8n}: Detects objects using the 80-class COCO taxonomy, with confidence threshold 0.45. Processing time: $\approx$80\,ms on CPU.
\end{itemize}

When a user attaches an image, it is decoded and resized (224$\times$224 for CLIP, 640$\times$640 for YOLOv8), processed by all three components, and their outputs combined into a \texttt{VisualContext} object prepended to the RAG query string. The CLIP embedding is also used as an additional query vector for FAISS retrieval.

\subsection{Interactive Terminal, IDE, and Debugger}
\label{subsec:websocket}

The WebSocket endpoint \texttt{/ws/terminal/\{project\_id\}} provides an interactive terminal through XTerm.js. The container remains alive until the user closes the terminal or a 10-minute inactivity timeout expires, preserving filesystem state between execution and interactive exploration. Monaco Editor's completion API is extended with a custom \texttt{AICompletionProvider} that queries the OmniRAG pipeline (debounced 400\,ms), allowing completions to incorporate knowledge from the user's uploaded documents. A Debug Adapter Protocol (DAP) implementation using Python's \texttt{Bdb} module supports breakpoints, step-over, step-into, step-out, and variable inspection, with DAP messages transported over the existing WebSocket using a dedicated message type prefix (\texttt{dap://}).

\subsection{AI Error Correction Loop}
\label{subsec:error-correction}

When a code execution returns a non-zero exit code, the error output is automatically fed back to the OmniRAG pipeline for root-cause analysis and correction. The corrected code is displayed as a diff in Monaco, which the user can accept with a single click. In evaluation, this loop autonomously corrected 73\% of syntax errors and 61\% of common runtime errors within one iteration.

\section{Memory Architecture}
\label{sec:memory}

\textbf{Short-Term Session Memory:} At natural pause points (90 seconds of inactivity or 20 turns), the LLM generates a hierarchical summary of the conversation history. Individual turn summaries (one sentence per turn) are compressed into a session-level paragraph, reducing context window token volume by 78\% relative to passing the raw message history.

\textbf{Long-Term User Profiles:} After each OmniRAG interaction, a structured record is stored in PostgreSQL (query, response, sources, complexity class, confidence score). A background Celery worker runs every 6 hours, aggregating each user's interaction records into a profile covering most-queried topics, most-accessed documents, preferred response length, and average query complexity tier. This profile is consulted by the query rewriter to personalise retrieval and generation.

\section{Analytics Workbench}
\label{sec:analytics}

The Analytics Workbench handles CSV/XLSX files up to 100,000 rows. Pandas performs automatic type inference; scikit-learn k-means (k=3 default, elbow method for automatic $k$) identifies natural groupings; Recharts renders scatter plots, histograms, and correlation heatmaps; the OmniRAG pipeline generates a natural-language insight summary conditioned on the computed statistics.

\section{Decision Vault}
\label{sec:decision-vault}

The Decision Vault implements the Evidence Quality Score (EQS) on a four-point scale:

\begin{table}[ht]
    \centering
    \caption{Evidence Quality Score (EQS) rubric.}
    \label{tab:eqs}
    \renewcommand{\arraystretch}{1.3}
    \begin{tabular}{cll}
        \toprule
        \textbf{Score} & \textbf{Label} & \textbf{Criteria} \\
        \midrule
        0 & Unsupported   & Claim made with no cited evidence \\
        1 & Weak          & Evidence cited but tangentially related \\
        2 & Adequate      & Evidence clearly relevant but incomplete \\
        3 & Strong        & Multiple converging independent sources \\
        \bottomrule
    \end{tabular}
\end{table}

When a user submits a decision rationale, the vault extracts individual claims via NLP, scores each against the EQS rubric, computes an aggregate mean score, and if aggregate $< 1.8$, generates a structured counter-argument targeting the weakest-scored claim. The adversarial response is framed as a devil's advocate challenge to encourage reflection rather than defensiveness.

\section{Authentication and Security Architecture}
\label{sec:auth}

Engunity implements dual-layer authentication: Supabase handles OAuth2 flows (Google, GitHub) and issues JWT tokens with 1-hour expiry; a local PostgreSQL user table maintains relational integrity. Security controls include Redis rate limiting (60 OmniRAG requests/minute, 20 Code Lab executions/minute per user), SQLAlchemy parameterised queries throughout, Docker SDK API calls (no shell subprocesses), MIME-type and archive-bomb validation for uploads, and Supabase Row-Level Security policies ensuring each user accesses only their own data.

\section{Frontend Architecture}
\label{sec:frontend}

The Next.js frontend follows the App Router pattern. Routes: \texttt{/} (landing), \texttt{/chat} (OmniRAG), \texttt{/research} (DeepResearchAgent), \texttt{/code} (Code Lab), \texttt{/analytics} (Analytics Workbench), \texttt{/vault} (Decision Vault), \texttt{/settings} (user profile and memory management). Global state is managed by Zustand stores per feature area. HTTP calls use Axios with JWT-attaching request interceptors and 401 token-refresh response interceptors. Framer Motion provides page transition animations. SSE responses are consumed using the native \texttt{EventSource} API with a custom React hook managing the stream lifecycle.
